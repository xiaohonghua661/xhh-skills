# code-comment-style — 代码注释写法约束

目标：让接手的人**不读实现也能看懂功能、数据怎么流、哪里改**。注释讲**意图与为什么**，不复述代码；排版对齐、可快速扫读，**不干扰代码审查**。

## 硬规则（必须遵守）

- 全中文注释，语义准确；不中英混杂（指令名、寄存器名、代码标识符等 token 例外）。
- 文件编码 UTF-8，**禁止 BOM**。出现乱码 / `?` / U+FFFD 立即用 UTF-8 无 BOM 重写。
- **保留已有有效注释**，不删除、不改变原意；只补齐与纠正。
- 注释必须与代码逻辑一致；逻辑变了同步改注释。禁止“废话注释”（复述代码本身）。
- 默认**简洁块注释 + 行内注释**；非必要不用 Doxygen（除非项目已统一或用户要求）。

## 必写三件

1. **文件头功能总览块**（每个源文件顶部）：模块用途、输入、输出、依赖、调用入口、（可选）数据流。
2. **函数傻瓜式说明块**（每个关键函数前）：功能、何时调用、输入、输出、影响的全局变量/外设。
3. **流程步骤注释**（关键流程段）：按 1 / 2 / 3 顺序说明每步做什么。

## 覆盖清单（逐项必有注释）

- 宏 / 枚举：每个值的含义、单位或范围。
- 结构体字段：每个字段用途、单位、默认值来源。
- 关键状态变量：含义 + 触发条件 + 影响对象。
- 分支判断：`if / else` 条件后补行内注释说明“为什么这样判断”。
- 硬件操作：说明原因（上拉 / 下拉、有效电平、时序、防误触 / 互斥）。

## 排版（保证不挡审查）

- 行内注释右侧**对齐成列**；参数说明用清单 / 表格式块注释，便于扫读。
- 缩进与现有文件一致（Tab 或空格二选一，不混用）。
- 注释块简短分段，避免长段落淹没代码。

## 模板

文件头：

```c
/* 模块说明
 * 功能: <这个文件干什么>
 * 输入: <数据/信号从哪来>
 * 输出: <结果去哪>
 * 依赖: <依赖的模块/外设>
 * 入口: <主要调用链，如 Init() -> SendCmd()>
 */
```

函数头：

```c
/* 功能: <做什么>
 * 调用: <何时/被谁调用>
 * 输入: <参数含义、结尾要求、取值范围>
 * 输出: <写到哪/返回什么>
 * 影响: <改动的全局变量/外设状态>
 */
```

行内（讲为什么，不复述代码）：

```c
HEAT_SET(0);   // 制冷时强制关加热，防止同时导通
```

## 溯源（代码源自外部文档时必写）

当函数、参数、流程、时序来自**官方文档**（数据手册、AT 指令集、协议规范、SDK 文档、外设手册）时，注释必须标明出处，二选一：

- **指向链接**：在文件头或相关段落写明官方文档 URL 与章节名，便于日后核对与升级。
- **同目录附文档**：把官方文档（或其摘录）放在同一文件夹，注释里指向该文件名。

关键参数若照抄文档（如广播间隔单位、寄存器位定义、协议字段），必须注明来源，防止日后不知其所以然、也方便文档更新后回溯校准。

## 禁止

- BOM、乱码、中英混杂、废话注释、注释与代码不符、删改用户原注释、无理由套 Doxygen、**源自官方文档却不标出处**。
